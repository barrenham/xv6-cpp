# 文件系统驱动 ELF 的契约

一个驱动 ELF 包含文件系统实现：格式识别、目录与对象管理、空间分配、读写、元数据、持久化和恢复。
内核提供 VFS、消息通道和预先打开的存储能力。驱动不是把类型名登记进去就完成了；每个声明支持的功能都必须有实际实现。

本轮目标是让驱动同时提供普通文件操作和自己的原生功能，而不为每个文件系统向内核增加命令分支。
已经落地 ext3 原生磁盘查询与第三方 ELF 自定义持久化命令。本轮没有实现 ext4 驱动，也不声称现有 ext3 后端覆盖 Linux ext3 的全部特性。

## 两类接口

| 接口 | 用途 | 实现位置 |
| --- | --- | --- |
| 标准操作 | lookup、目录枚举、创建、读写、截断、属性、链接、改名、同步、引用释放 | ELF 的 Backend 回调 |
| 驱动原生操作 | 文件系统自己的查询、管理操作、扩展属性或其他自定义能力 | ELF 的版本化命令命名空间 |

标准操作仍受宿主系统 VFS 语义约束。原生操作通过同一个打开文件/目录定位所属实例，不能指定其他挂载的对象编号。
内核不解析原生命令的数据，不检查类型名是否为 ext3/ext4/FAT，也不实现格式算法。
ELF 可以链接自己的静态库；所有依赖必须适配本系统用户态 ABI，不能直接执行 Linux ELF 并期待 Linux 系统调用存在。

## 原生命令通道

公共 C 接口见 `user/fs/sdk/include/xvfs/control.h`。对已打开的文件或目录使用 `XVFS_CONTROL_IOCTL`，
或调用 `xvfs_driver_control(fd, &request)`。

请求字段：size、载体 version=1、driver_version、command、input_size、capacity、output_size、
32 字节 NUL 终止 interface_name，以及 512 字节 data。input_size 与 capacity 分别指定输入长度和输出空间。
输入和输出共用 data，驱动需要先消费输入再覆盖它。成功返回输出字节数并填写 output_size；失败返回负数。
载体沿用当前系统的 -1 错误返回；需要区分业务状态的命令应在正常响应中定义状态字段。
输出未使用的 data 字节清零。输入、输出容量、命名空间、版本、指针以及回复长度均验证；失败不保证已经发生的存储修改回滚。

内核转交以下不能由请求方伪造的上下文：原调用者 pid/uid/gid、描述符 Readable/Writable，以及挂载 ReadOnly。
驱动必须按每个命令的语义检查权限；不能因为自己的服务进程是 root，就把客户端也当作 root。
修改文件内容的命令应尊重描述符读写权限；文件系统级管理命令应明确所需的管理权限，所有修改都必须遵守只读挂载。文件描述符继承后的调用仍携带当前执行者身份。

C++ SDK 的 `Backend::control(node, interface, version, command, access, input, input_size, output, capacity)`
实现原生命令，返回输出长度或负数。数据缓冲可别名。只有显式声明 Control 操作位的驱动才接收该操作；
原来按协议 3 注册的驱动不会自动得到这个能力。协议 3 的消息布局不变，新增可协商的 Control 操作 17。

成功回复必须携带该打开对象的最新 Attributes，且对象编号和类型保持稳定。C++ SDK 自动调用 getattr；
直接实现 C 协议的驱动需要自己填写。内核校验并刷新共享 inode，使原生命令改变长度后 SEEK_END 等操作立即看到新值。
改变其他对象、全局布局或持久化策略的命令需要驱动维护自身一致性；该通道不提供自动事务回滚或任意 VFS 缓存失效协议。

每条消息受协商载荷上限约束，单次 RPC 有现有 5 秒无响应期限。大数据应设计分块命令；耗时管理操作可返回任务编号、
由驱动分批执行并提供进度查询，不能在单次请求里无限阻塞。新功能的数据格式、子命令和兼容策略都属于驱动规范。

## 发现能力和使用工具

命名空间 `xv.fs.driver`、版本 1、命令 0、空输入返回 `xvfs_driver_info`：
结构大小、描述版本、wire 版本、驱动标志、操作位、载荷信息及主要原生命名空间和版本。
C++ SDK 提供公共描述处理；第三方 C 驱动按同样布局回复。驱动也可在自己的命名空间中列举更细的功能。

```sh
fsctl /
fsctl / ext3.native 1 1
fsctl /data/some-file ext3.native 1 2
```

无显式命名空间时显示描述信息；显式命令显示十六进制结果。
`fsctl -w path interface version command HEX` 使用可写描述符并发送十六进制输入。
不能仅根据类型名称推断某项功能已经实现，调用方必须检查描述版本、能力及具体命令的结果。

## 已有的真实驱动实现

`ext3.elf` 的普通操作仍由用户态 Volume/JBD 引擎完成；它自己的 `ext3.native` 版本 1 提供：

- 命令 1：读取真实超级块，返回块/空闲块、inode/空闲 inode、块大小、兼容特征位、日志 inode 和 UUID。
- 命令 2：读取当前对象的真实 inode，返回 64 位磁盘长度、inode 编号、flags、分配扇区、时间戳、generation 和外部属性块编号。

输出结构见 `user/fs/sdk/include/xvfs/ext3.h`。这些结构及字符串仅出现在用户态驱动/客户端，不在内核控制分派中。
当前 Volume 会拒绝含外部 ACL 块的 inode，因此该字段在已支持的 inode 中为零；这不是 xattr 读写支持。
查询 flags 也不等于已经支持设置这些 flags。

`examples/fs-plugin/` 的 C 驱动自行定义 `example.file`：状态查询，以及对可写源文件的持久化前缀写入。
后者检查真实 uid、可写描述符、只读状态，写入后 fsync 再回复；普通 read 和重启后重新挂载都能看到结果。
它用于验证未知原生命令无需内核改动，不是另一个成熟磁盘文件系统的实现。

## 编写 ext4 等新驱动时的完成标准

新 ELF 需要实际实现和验证自己的格式特性，并拒绝尚不支持的磁盘 incompatible/readonly 特征，不能仅声明一个 ext4 名称。
日志恢复、孤儿回收、分配与目录一致性、错误传播和持久化均由驱动负责。正常回归、故障注入和与外部格式工具交叉检查属于验收内容。

原生命令可承载新的用户态功能，但不能自动赋予内核尚无的文件映射、阻塞文件锁或 Linux 完整 syscall 语义。
现有标准 VFS 属性/编号仍为 32 位；原生命令可以返回自己的 64 位属性，但这不意味着标准文件 I/O 已支持大于 4 GiB 的文件。
遇到需要内核共用机制的能力，应扩展通用接口与相应系统调用，而不是添加按 ext4 等名称分支的实现。

构建、清单、安装和根插件引导见 [插件开发规范](fs-plugin-authoring.md)。
