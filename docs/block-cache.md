# 块缓存索引、锁拆分与对照测量

本轮保持 30 个 1KiB 缓冲块及同步块 I/O 语义，优化缓存查找和并发访问。没有靠扩大缓存容量获得性能差异，也没有更改 ext3 日志提交、flush 或 fsync 的持久化规则。

## 原先的路径

LruBlockCache 用一把全局自旋锁保护整个缓存的身份、引用数和双向 LRU 链表。读取即使命中，也要持锁沿链表比较 `(设备号, 块号)`；归还块、pin 和 unpin 都进入同一把锁。多个 CPU 读不同块时，仍会争用这把锁。

未命中时在同一锁内从 LRU 尾寻找未被引用的缓冲块，替换身份，再释放全局锁并获取该块的 SleepLock。这个“发布身份后再等待块内容”的顺序允许多个相同请求合并为一次实际 I/O，优化后保留。

## 当前结构和锁协议

查找索引改为 31 个哈希桶，键同时包含设备号和块号。桶数不等于缓存容量，数据缓冲块仍为 30 个。每桶有自己的锁、链表和统计，桶按缓存行对齐；不存在每次命中都要修改的全局 LRU 链表或全局统计计数器。

命中路径只持有一个桶锁，增加引用数后释放，再获取块的 SleepLock。不同桶上的命中无需进入淘汰锁。SleepLock 继续串行保护同一块的内容、valid 状态与实际读写。

未命中先放掉桶锁，再获取独立淘汰锁，随后重新检查目标桶。另一个请求可能已发布同一身份，重查命中时借用该对象，不能再创建第二个缓冲块。需要替换时，顺序为“淘汰锁 → 目标桶锁 → 原身份桶锁”；只有淘汰锁的唯一持有者能同时持两个桶锁，其他路径不会拿着桶锁等待淘汰锁。因此没有反向锁环。等待 SleepLock 或设备 I/O 时，不持有这些缓存自旋锁。

淘汰候选按最近归还/最后 unpin 的时间批量整理，候选列表由淘汰锁独占。每次取用前，在当前所属桶锁下重新检查引用数为零且时间戳未变化；被其他 CPU 重新使用的候选作废。用完一批才重新整理，避免每次冷未命中都扫描全部缓冲块。并发情况下这是基于时间快照的 LRU 近似，不承诺全局严格的逐次 LRU 顺序。

缓冲块地址固定。一次正常借用或 pin 都使引用数非零，阻止身份迁移；最后归还与 unpin 才能使它重新成为候选。所有缓冲块均被占用时，保留原来的显式容量耗尽错误，没有偷偷复用活跃或固定的块。初始未分配状态单独记录，设备 0、块 0 不会被误认为已存在的有效身份。

## 运行时统计

`cat /proc/bcache` 查看根磁盘缓存的启动累计统计。每个 LruBlockCache 实例都维护相同统计接口；此 proc 文件当前展示根缓存，不合并第二块数据盘的缓存。

| 字段 | 含义 |
| --- | --- |
| hits / misses | 第一次查询时已有/没有该键；两者之和是逻辑查询次数 |
| evictions | 复用了已经分配过身份的块；首次分配不计淘汰 |
| lookup_steps | 查找目标键的比较次数，包含并发未命中后的重查 |
| reads / writes | 实际下发给块设备的读取/写入次数 |
| eviction_steps | 整理和检查淘汰候选时检查缓冲块的次数 |
| locks | 已完成的索引/淘汰锁获取次数，不包含块 SleepLock |
| contentions / spins | 首次尝试失败的获取次数 / 失败原子交换次数 |
| wait_ticks / tick_hz | 检测竞争后到获取锁的累计经过时间及其时基 |

根缓存的 `tick_hz=10000000`。等待时间是累计经过时间，可能包含持锁者或等待者被宿主机调度的影响，不等同于 CPU 自旋耗时。原生测试时钟使用纳秒。无竞争的获取不读时钟，避免统计本身给每个缓存操作增加计时调用。

已有键命中不代表内容已经就绪：命中的块可能正在读盘，该请求仍需等待它的 SleepLock。多个逻辑未命中也可能在重查时合并。因此 hits/misses、物理 reads 和等待应分别解释。

统计按桶使用原子计数，快照逐项读取，不停止其他 CPU，也不是全系统原子瞬间。读 proc 文件自身的路径查询也可能访问根缓存，前后差值应留意这一观测开销。

## 对照方法

线性基线保留旧的全局锁、线性查询与双向 LRU，只加入同样的统计、明确的未分配状态和相同的锁竞争测量方法。探测次数在一轮扫描结束后汇总，避免基线逐节点更新统计而新版只更新一次，造成不公平的计时差异。

[基线补丁](block-cache-linear-baseline.patch) 仅供隔离构建；[构建工具](../tools/build_cache_baseline.py) 会复制源码到指定目录并在那里应用，不改开发目录的实现。

```sh
python tools/build_cache_baseline.py --output build/cache-linear --native
python tools/profile_block_cache.py \
  --qemu /usr/bin/qemu-system-riscv64 \
  --baseline build/cache-linear/kernel/kernel.elf \
  --kernel build/dev/kernel.elf --image build/dev/fs-test.img \
  --rounds 2 --output build/cache-comparison/measurements.json
```

对照包含两层：

- 原生缓存层：同一内存块设备，每项总计 200000 次，四线程场景分担总操作数。使用重复热读、顺序读、伪随机读及独立块的并发热读，校验返回数据。
- 真实 QEMU 文件层：同一 ext3 种子、同一测试程序与离线预置数据，1/5 核各运行两轮。每项共读 2048 个 1KiB 块；重复读使用 16 块，顺序/随机使用 128 块，多进程由四个子进程读取各自文件。记录客体耗时、QEMU 进程 CPU 时间和缓存计数。随机索引使用 LCG 高位，包含短距离重用。

数据文件在私有磁盘上离线准备，准备过程不进入读性能计时，也不修改传入镜像。实际文件读取还包含路径、inode、用户复制、系统调用与调度成本；ext3 当前每块读操作仍经过文件系统 core 锁，缓存层并发改善不能直接当成文件系统整体加速。CPU 指标为 Linux 累计的 QEMU 进程 user+system 时间，包含全部 vCPU/设备线程，不是缓存函数独占 CPU 时间。

## 完整性验证

原生契约覆盖同一冷键 8 线程竞争只读盘一次、设备/块 0、不同设备身份分离、pin 后淘汰压力、8 线程修改与淘汰时不丢失 16000 次增量、最后可借用全部容量，以及容量耗尽的原有错误。文件系统、日志恢复、真实 QEMU 读取和数据校验另作验证。fork 性能门禁不运行；这里的四进程测试测量读取，包含一次性的进程创建成本。

## 实测结果

下表是同机顺次运行的中位数：原生各三轮，QEMU 各两轮，不是统计置信区间。原生并发用四线程；QEMU 并发用四个用户进程。二者工作量不同，只比较同列前后。

| 负载 | 原生旧版 / 新版（ms） | QEMU 1 核旧版 / 新版（s） | QEMU 5 核旧版 / 新版（s） |
| --- | ---: | ---: | ---: |
| 重复读 | 76.64 / 102.08 | 3.64 / 3.68 | 3.79 / 3.22 |
| 顺序读 | 158.37 / 264.53 | 22.76 / 25.94 | 10.52 / 9.43 |
| 随机读 | 129.76 / 213.78 | 17.09 / 19.53 | 8.58 / 8.40 |
| 四线程 / 四进程读 | 395.41 / 89.75 | 3.64 / 3.51 | 3.68 / 3.42 |

原生四线程热读约加速 4.41 倍。单线程原生重复、顺序、随机负载反而变慢，说明 30 块的小容量下，哈希计算、时间戳及多锁交接仍有成本。QEMU 五核文件层四项中位数约改善 2%～18%；单核顺序和随机读约慢 14%。不能将这次改动描述为所有工作负载均加速，也不能把原生并发倍数当作应用加速倍数。

原生并发的锁竞争次数中位数由 212553 降为 9235，累计等待从 1094.86ms 降为 10.16ms。顺序读查找比较次数由 6000000 降为 393736，但额外管理开销抵消了查找节省。后续应优先处理 miss 路径和 ext3 core 锁，而不是单纯增加桶数。

完整原始轮次、计数、QEMU CPU 时间、内核与输入镜像 SHA256 保存在 [验收记录](block-cache-acceptance.json)。隔离重建的线性基线已实际编译通过。


## 本轮验收与使用

16 项相关回归全部通过：镜像布局、文件系统契约、锁契约、启动、单/五核 PTY、poll、TTY、rootfs 更新、ext3 日志/卷/镜像工具、终端与 printf 契约。缓存并发与 printf 契约另外通过 ASan/UBSan（含泄漏检查）。串口 procfs 与 1920×1080 GPU 画面各在单/五核通过列宽及真实 Tab 验证。

当前开发内核已构建；持久 rootfs 已备份并仅更新 `/bin/ps` 和 `/bin/free`，逐字节核对安装结果；`/etc`、`/home`、`/root`、`/data` 内容与属性保持一致。启动新版内核后使用 `cat /proc/bcache` 查看统计。性能测试始终使用私有镜像；未运行 fork 性能门禁。
